ISSUE 3 — TIMEOUT WITH NO AUTO-RETRY
Root cause: single attempt with no retry logic.
Bad UX to ask user to try again manually.
════════════════════════════════

STEP 1 — Add automatic retry in the API route.
In /api/chat/route.ts for analyse mode:

const MAX_RETRIES = 2;
const TIMEOUT_MS = 25000;

async function runPipelineWithRetry(
  address: string, 
  attempt: number = 1
): Promise<PipelineResult> {
  try {
    const controller = new AbortController();
    const timeoutId = setTimeout(
      () => controller.abort(), 
      TIMEOUT_MS
    );
    
    const result = await runPropertyPipeline(address);
    clearTimeout(timeoutId);
    return result;
    
  } catch (err: any) {
    const isTimeout = err.name === 'AbortError' || 
                      err.message?.includes('timeout');
    
    if (isTimeout && attempt < MAX_RETRIES) {
      console.log(`Pipeline timeout, retry ${attempt}/${MAX_RETRIES}`);
      // Wait 2s before retry
      await new Promise(r => setTimeout(r, 2000));
      return runPipelineWithRetry(address, attempt + 1);
    }
    
    // All retries exhausted — return partial result
    // rather than throwing completely
    if (isTimeout) {
      return {
        partial: true,
        error: 'timeout_after_retries',
        // Return whatever data we have from fast sources
        // (LINZ usually responds quickly even if scrapers don't)
      };
    }
    
    throw err;
  }
}

STEP 2 — On partial result, still generate a report.
If pipeline returns partial: true, pass to Claude with:

"NOTE: Some data sources timed out. 
Work with available data only. 
Mark missing sections as 'Data retrieval timeout — 
please try again for complete analysis.'
Still generate the report with whatever data is available."

STEP 3 — Update loading UI.
In the mobile app AnalysisProgress component:
If retry is happening, update the status message:

"Data sources responding slowly — retrying..."
"Retry attempt 2 of 2..."

Do NOT show the user a failure message unless 
all retries are exhausted AND no partial data exists.

If all retries fail with zero data:
Show inline in chat (not a toast):
"Analysis failed after 2 attempts. The property 
data APIs may be temporarily slow. 
[Try again ↻]" 

The [Try again] button resends the same message 
automatically — user doesn't have to retype.

ISSUE 5 — INPUT NOT CLEARING AFTER SEND
Root cause: input state not being reset after send.
════════════════════════════════

In ChatInput component (React Native):

const [inputText, setInputText] = useState('');
const inputRef = useRef<TextInput>(null);

const handleSend = async () => {
  if (!inputText.trim() || isLoading) return;
  
  const messageToSend = inputText.trim();
  
  // Clear input IMMEDIATELY before async operations
  setInputText('');
  inputRef.current?.clear(); // Also call .clear() for safety
  
  // Dismiss keyboard on send
  Keyboard.dismiss();
  
  // Now process the message
  await sendMessage(messageToSend);
};

<TextInput
  ref={inputRef}
  value={inputText}
  onChangeText={setInputText}
  onSubmitEditing={handleSend}
  ...
/>

The key fix: setInputText('') must happen BEFORE 
the await call, not after. Otherwise React batches 
the state update and it appears to not clear.

ISSUE 6 — SCROLL STUCK ON REPORT CARDS
Root cause: nested scroll views competing for 
touch events. When finger lands on a child 
ScrollView or touchable inside the report, 
the parent FlatList doesn't receive scroll events.
════════════════════════════════

STEP 1 — Fix scroll competition in FlatList.
In the main chat FlatList:

<FlatList
  ...
  // These two props fix nested scroll competition:
  nestedScrollEnabled={true}
  keyboardShouldPersistTaps="handled"
/>

STEP 2 — Wrap FeasibilityReport in a ScrollView 
that passes scroll events to parent:

// In FeasibilityReport.tsx (React Native version)
<ScrollView
  scrollEnabled={true}
  nestedScrollEnabled={true}
  // This is the key prop — allows parent to scroll
  // when this component's content is fully visible
  onStartShouldSetResponder={() => false}
  onMoveShouldSetResponder={() => false}
>
  {/* report content */}
</ScrollView>

STEP 3 — Make all touchable areas within report 
NOT intercept scroll gestures:

For AccordionSection headers (TouchableOpacity):
<TouchableOpacity
  activeOpacity={0.7}
  onPress={toggle}
  // Don't steal scroll gestures
  delayLongPress={500}
>

STEP 4 — Alternative approach if above doesn't fix it:
Convert the FeasibilityReport from a nested ScrollView 
to a flat list of sections that the parent FlatList renders:

Instead of rendering <FeasibilityReport> as one item 
in the FlatList, render each section as a separate 
FlatList item. This completely eliminates nested 
scroll competition because there's only one scroll 
view in the hierarchy.

reportSections = [
  { type: 'header', data: report },
  { type: 'scores', data: report.scores },
  { type: 'overlays', data: report.overlays },
  { type: 'asbestos', data: report.asbestos },

messages.flatMap(msg => 
  msg.type === 'report' 
    ? expandReportToSections(msg.report)

use this approach if scrolling is still unreliable.
